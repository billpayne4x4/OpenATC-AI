# Current Rust architecture

The Rust workspace owns the deployed Linux plugin and companion engine. The earlier top-level C++ implementation and CMake build have been removed; shared regression fixtures remain. The engine owns plan, staged clearances, transcript, settings, controller roster and loaded airports. Network/model calls occur outside the shared state lock. The plugin transports telemetry and UI actions over local HTTP and uses the X-Plane SDK only on the simulator thread.

The plugin starts a detached local engine with its simulator PID. A joined background worker sends wall-clock heartbeats every two seconds independently of flight-loop pause. Disable requests local shutdown. A plugin-owned engine exits after its host disappears or heartbeats expire, with startup grace. Manually started engines and remote AI/STT/TTS services are separate and remain running. Plain plugin transport avoids bringing TLS libraries into X-Plane; the engine proxies provider requests.

Audio uses native device enumeration with cached IDs. Linux prefers PulseAudio/PipeWire and excludes monitor sources from capture; ALSA is a fallback. Playback honours WAV sample rate and role gain. Dataref discovery supports numeric scalars/arrays; the vendored X-Plane wrapper fixes an inverted type-mask test. The A20N ToLiss profile supplies power/radio references and standard writable COM1 tuning.

The shared UI supports simulator and desktop rendering. Local Frequencies and the airport search have independent state. Selecting a frequency queues COM1 tuning. Taxi loads scenery runways, curved pavement, taxi graphs and stands; approval is distinct from route calculation. Map arrows and opt-in terrain-following SDK instances use the approved network path. Unverified stand connectors do not receive ground arrows. Terrain footprints are probed on the SDK thread; unsafe/discontinuous surfaces are skipped. Night textures make arrows visible without adding scenery illumination.

Arrival loads the destination independently. Planned geometric descent ends at the selected landing threshold; current descent uses live vertical speed and true-ground-track closure. Incremental cached terrain probes provide centre-line ground, corridor envelope and a horizontal highest-known-ground-plus-2,000-ft reference. Missing samples remain gaps. Regional transition altitude and a published ILS initial-final altitude are references, not a computed transition level or fully constrained STAR/VNAV path. The airport browser ILS beam also depends on available published glide-angle data.

Speech is open data under `speech/`: global crew files, common ATC material and regional IFR/VFR/shared material. Recursive loading validates metadata and unique IDs. `profile.toml` longest-prefix routing selects a phraseology variant; folder scopes prevent IFR/VFR and regional leakage. Neutral phrases are shared. Entries are examples, not an operational procedure database. Crew prompts and `/suggest` consume examples; normal requests use staged controller logic; initial departure clearance/start/pushback wording is rendered from checked TOML entries with live slots. `/suggest` returns a proposal without applying a plan effect. The plan currently lacks flight-rules state, so that API defaults to IFR unless supplied explicitly.

`Slots.extra` supplies context beyond the legacy slots. New values include their spoken units. Checked rendering refuses missing context; illustrative prompt values are never live facts. Compiled system rules constrain `/suggest`; editable crew/classifier prompt files load on restart. `prompts/atc_reply.txt` is presently an authoring reference, not the loaded controller-system prompt. See [speech editing](../speech/README.md) for scopes, schema, references and boundaries.

Current navigation/scenery, verified controller state and aircraft-specific procedures must determine operational eligibility. A new TOML phrase cannot implement separation, runway crossings, CPDLC, emergency response or an aircraft action. Country/FIR and airport procedure review remains separate from coarse phrasebook routing. See [validation](VALIDATION.md) and [remaining work](ROADMAP.md).

The shared `core::stations` module indexes enabled scenery in priority order, resolves frequency reuse to the nearest receivable airport and supplies the same horizon/service-cap model to the UI and request gate. Service caps are Delivery/Ground 25 NM, Tower 50 NM, ATIS 100 NM, Approach/Departure 150 NM, further limited by the geometric horizon with a 10 NM airport floor. Terrain shielding, controller sectors and non-airport remote sites are not modelled. Water/heliport-only station coverage remains incomplete because the airport geometry loader currently requires land runways.

`plugin::weather` alone queries airport surface locations via SDK 4.0 on the main thread. Timestamped samples feed `engine::radio`; online planning weather cannot flow into live ATIS. The UI serialises ATIS with other speech and cancels it through the Rust audio worker on reception changes. The request gate is unconditional even where legacy realism settings would bypass frequency checks. Network waits do not hold the session lock; reception is checked again immediately before a controller decision. Optional model wording retains deterministic decisions and accepts only unchanged operational tokens.

The Rust audio and HTTP/client workers now support cancellation during pending synthesis/transcription and state/command requests. Audio workers are joined before freeing their backend context; client workers are joined before plugin unload. This prevents delayed ATIS from playing after retuning and avoids freeing resources underneath active workers.

Channels also reads published controllers from enabled scenery `atc.dat` files and the active custom/default ATC navdata. Tower controller definitions replace scenery Tower frequencies; Ground/Delivery remain from airport scenery. Approach and Center discovery uses published horizontal coverage plus a simulated 150 NM regional network reception margin. Assigned controller altitude bands do not prevent tuning from the ground; actual transmitter locations and terrain shielding remain unmodelled. Center rows show “Sector coverage” rather than a misleading distance to a polygon centre. No controller or frequency is invented; regional transmitter locations and terrain shielding are not modelled.

Airport capabilities are assigned after ATC indexing and before optional user overrides. Clearance is handled by a published Delivery station, otherwise Ground, otherwise Tower. Where no Ground is published, Tower handles ground duties. Primary station names and frequencies remain unchanged. Separate services still require tuning the appropriate controller. The SDK `sim/atc/com1_tuned_facility` exposes the primary tuned role, not a complete combined-duty list.

IFR clearance messages explicitly request readback. Spoken readback matching checks NATO callsign/destination, route, altitude, squawk and runway; unclear values receive say-again rather than a phase error. Taxi instructions remain pending until readback is accepted. Ground guidance ends when stopped within 25 metres of the route endpoint. Protected runway edges are excluded; a reachable identified crossing hold point may end a partial route, without crossing permission. The UI registers a native system clipboard backend for external text-field copy/paste, with persistent ownership. Live simulator voice and clipboard interaction remain user acceptance checks.

Live controller responses, readback prompts/corrections, taxi instructions, ATIS/weather wording, crew fallback replies, copilot callouts and background exchanges now come from `speech/runtime/responses.toml` (191 templates, 381 phrases). The regional/crew example library retains 476 situations and 1,420 phrases. Runtime alternatives preserve named fact placeholders; startup rejects missing responses or changed placeholder contracts. Phrase edits do not change Rust authorization logic. Taxi readback uses structured taxiway/hold-short facts, so editable wording is not parsed as route data. An isolated engine regression edits the TOML acknowledgment and verifies that exact edited text is returned; invalid placeholder alternatives are rejected.

ATC Auto Reply sits beside Replay ATC. It submits a complete pilot readback using the active IFR/taxi clearance, or acknowledges start-up/pushback approval once. It excludes exchanges addressed to background traffic. It is disabled when no reply is pending. Pilot reply wording is editable in `speech/runtime/responses.toml`; operational values and authorization remain in Rust. Click a chat message to open a read-only selectable text box; use Ctrl+C for a selection or Copy message for the whole line.

Taxi loading prefers published scenery ATC graphs. When absent, it derives an unnamed graph from solid/enhanced painted centerlines (apt.dat styles 1/7/51/57), samples Bezier curves and intersects connected lines. Pavement gaps, edge markings and hold barriers do not become ordinary taxi links. The UI identifies this fallback. Fallback stand connectors are limited to 35 metres of continuous pavement; hold-line buffers allow room ahead of the aircraft reference point.

A holding point away from the departure threshold ends the ordinary taxi route and requires separate Tower backtrack clearance. Request runway backtrack becomes available while stopped at that route endpoint. At airports without a taxiway graph or holding point, Tower can issue runway taxi/backtrack to the assigned departure end over verified pavement and the selected runway centerline. Ground must hand the request to Tower; no specific airport is hardcoded. Backtrack clearance requires readback, grants no takeoff permission, and the arrows stop when the aircraft reaches the end. Other runway crossings, disconnected pavement and overlap with another runway are rejected. Simulator-reported runway occupancy and final-approach protection are implemented; traffic ownership and full separation remain future work.

At the approved taxi endpoint, stopped within 25 m, the engine checks the actual tuned airport station. Ground hands off to the published Tower frequency; Tower issues departure clearance when simulator-reported traffic is clear, or holds for runway occupancy/final traffic. Missing traffic data keeps the aircraft holding. Pausing, radio power off, untuned channels and other airports cannot trigger departure. Holding for traffic is reconsidered when the runway clears. Routes needing backtrack or another runway crossing retain their hold restriction and require further explicit permission. Scenery-owned runway guard lights remain unchanged. Duplicate plugin holding-light markers have been removed; no per-holding-point native lighting control has been established. TCAS targets omit ownship and do not include traffic hidden from X-Plane’s traffic interface; this is not full traffic sequencing or wake separation.

## New flight and lifecycle

The header's New flight action clears flight-specific engine and UI state while retaining settings, phrase history and controller voices. A generation counter rejects responses started before the reset. The plugin clears its crew callbacks and guidance caches when notified; simulator controls are not restored or changed by reset.

Disable stops the flight loop, heartbeat and local interface. The SDK window and renderer are retained for re-enable, so there is only one active ImGui context. Enable rebuilds simulator bindings and resumes the companion connection. Plugin commands and its menu are registered once. The remote AI server is independent of this lifecycle.
